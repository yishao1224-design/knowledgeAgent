# langchain-ai/openwiki README (condensed capture)

Faithful condensation of the project README (raw `main/README.md`) as
fetched 2026-11-10. Supersedes the 2026-07-12 capture for current
claims. The README states no release version number (only a dynamic
npm-version badge); it requires Node.js 22.22.0 or newer, is MIT
licensed, and is "Built with Deep Agents" (`langchain-ai/deepagentsjs`).
It does not state the implementation language.

## What it is

Tagline: "A living wiki for your code, your agents, and you."
OpenWiki "turns your codebase and knowledge sources into a linked
Markdown wiki that you own." A coding agent uses it to understand a
repository, answer questions, and find context across related
projects; humans can read the same pages or explore them as an
interactive graph. For repository wikis it "tracks facts back to
source evidence so updates can focus on what changed."

Two entry points: start **inside your coding agent** (recommended:
"the easiest way to get started"), or use the **standalone CLI** for
repository docs, personal knowledge, and scheduled updates.

"What's new" list: linked wiki workspaces (`openwiki link`), more
coding-agent integrations, parallel page workers, resumable updates and
grounded Claims; plus "Portable OKF v0.2 output" and publishable
visualizers.

Install: `npm install -g openwiki` (Windows: npm or pnpm; installing
with Bun can fall back to compiling `better-sqlite3`, needing Visual
Studio Build Tools).

## Coding-agent integrations (host-driven runs)

`openwiki integrations install <host>` for Codex (`codex`), Claude Code
(`claude`), OpenCode, Cursor, IBM Bob / Bob Shell (`bob`), Kiro, Oh My
Pi (`omp`), Antigravity, GitHub Copilot CLI (`copilot`); Pi installs
via `pi install npm:openwiki`. User-level by default; `--project [path]`
for repo-scoped state; `integrations list` / `uninstall`.

- Inside the agent, OpenWiki "uses that agent's authenticated model
  session and repository tools, so there is no separate model provider
  to configure."
- Workflow: ask the agent to "Initialize this repository's OpenWiki
  from the current source and tests"; it writes `openwiki/`, tracking
  source evidence and saving progress per page.
- Scope limits: host-driven runs "currently support repository code
  wikis, not personal brains"; connector-sourced context (incl.
  LangSmith) not yet supported.
- Division of labour: the host agent investigates, plans and writes
  pages sequentially with its own tools; OpenWiki "owns the durable
  queue, Claims validation and persistence, source-drift handling, and
  deterministic finalization of Claims, indexes, provenance, setup
  files, and metadata."
- MCP lifecycle: `openwiki_begin → openwiki_submit_plan →
  openwiki_next_page → openwiki_submit_page → … → openwiki_finish`,
  optional `openwiki_inspect_page_claims`. Host submits sparse Claim
  decisions (confirm / revise / add / retract); OpenWiki refuses to
  finish until the final state is durable.

## Retrieval and workspaces

- `openwiki_search` (ranked compact results) and `openwiki_read`
  (full sections): local, read-only, model-free MCP tools. Framed as
  "optional context, not a routine step at the start of every task."
- `openwiki link` groups existing repo wikis into named workspaces
  (e.g. control plane + data plane + infra); search spans members.
  Registry under `~/.openwiki`. `openwiki workspace use|current|clear`
  sets the active workspace; ambiguous membership returns
  `workspace_required`. Discovery tools: `openwiki_list_workspaces`,
  `openwiki_list_wikis`.

## Visualizer

`openwiki visualize` serves `./openwiki` on `127.0.0.1` (default port
4321) as a node graph plus live Markdown reader; `--export <dir>`
writes a static, hostable copy. Loads libraries from a public CDN.

## Two modes (standalone CLI)

Bare `openwiki`, `--init`, `--update` default to **code** mode; add
`personal` (or `--mode personal`) for the personal brain.

| Mode | Documents | Writes to | Start |
|------|-----------|-----------|-------|
| Code (default) | current repository | `openwiki/` in the repo | `openwiki --init` |
| Personal | connected sources | `~/.openwiki/wiki` | `openwiki personal --init` |

Standalone runs use OpenWiki's own Deep Agents documentation agent;
first run picks provider, credentials, model. `-p` / `--print` gives a
one-shot run. Re-running `--init` replaces the generated wiki and
Claims while preserving user-authored `openwiki/INSTRUCTIONS.md`.
Interrupted runs resume from `openwiki/.run.json` (persistent
checkouts; ephemeral CI starts fresh).

Parallel page workers: `OPENWIKI_PAGE_CONCURRENCY` (default 1, range
1–8) for native CLI runs; a rate-limited worker lowers concurrency by
one; retries default 3 (5 when concurrency > 1), override with
`OPENWIKI_PROVIDER_RETRY_ATTEMPTS`. LangSmith traces group per run.

State directory: `~/.openwiki` by default (credentials, personal wiki,
connector data, conversation history, skills); override with
`OPENWIKI_CONFIG_DIR`.

## Repo-root agent files and ownership ("How it stays yours")

- "On each `code` run, OpenWiki maintains an `AGENTS.md` at the repo
  root, and refreshes `CLAUDE.md` when the repository already has
  one." It does not create `CLAUDE.md` (Claude Code falls back to
  `AGENTS.md`). Managed instructions point agents at
  `openwiki_search`/`openwiki_read`, with `openwiki/quickstart.md` as
  fallback. It "only rewrites its own `<!-- OPENWIKI:START -->…<!--
  OPENWIKI:END -->` block and leaves the rest of each file untouched."
- Versioned claim sidecars under `openwiki/.claims/` travel with the
  Markdown.
- `openwiki/INSTRUCTIONS.md`: user-authored brief, never rewritten in
  normal runs.
- "No-op runs do not churn docs": a clean update skips model work and
  only refreshes `.last-update.json`.
- Provider choice, keys, LangSmith tracing saved to `~/.openwiki/.env`.
- `.openwikiignore` (gitignore-like syntax) is a read boundary: ignored
  paths are never read, scanned, or reproduced.

## How it works

Repository generation is "an ordered queue of independently durable
page jobs" (concurrent in native CLI, sequential via coding agents).
`openwiki/.run.json` checkpoints the run; a page advances only after
its Markdown, Claims, verification and `openwiki/.page-manifest.json`
entry are durable.

### Grounded Claims (staleness handling)

- Facts behind each repository page are tracked as "Grounded Claims".
  "Each Claim points to versioned source evidence, such as
  `repo://src/server.ts#L40-L82`. When that evidence changes or
  disappears, OpenWiki identifies which facts need to be confirmed,
  rewritten, or retired."
- Claims cover behavior, responsibilities, architecture, data flow,
  invariants, failure semantics, configuration, security boundaries;
  each records the evidence version observed when established, "rather
  than relying only on when a Markdown file was last generated."
- Before an update, every persisted evidence version is checked; a
  stale or unresolved Claim forces work on its owning page by default
  (`deferUnplannedClaimIssues: true` allows a focused update that
  leaves the run marked interrupted). Workers receive only Claims
  needing attention; they confirm, revise, add, or name retractions.
- Updates use "repository changes since its last successful run and
  any stale Claims"; clean updates skip model work.
- Scope: Grounded Claims "currently apply to repository code wikis and
  repository evidence. Connector-derived facts, including
  LangSmith-only observations, are not claimed."

### OKF v0.2 output

"OpenWiki emits Google Open Knowledge Format (OKF) v0.2 bundles in both
modes, so your wiki is portable to any OKF-aware tool." (README links
the spec at `GoogleCloudPlatform/knowledge-catalog/.../okf/SPEC.md`.)

- Every concept document has YAML front matter with a non-empty `type`.
- `generated: {by, at}` stamped on new pages, advanced on any body
  change; producer `openwiki/<version>` (or the coding-agent host).
  Legacy v0.1 `timestamp` tolerated.
- Repository pages project Claims evidence into `sources`, preserving
  independently authored entries.
- `verified: {by: openwiki/<version>, at}` only after a successful page
  submission with a complete non-empty Claims set and final evidence
  recheck; "Clean preflight alone never creates or advances
  verification."
- "The optional v0.2 provenance, trust, and lifecycle families
  (`sources`, `verified`, `status`, `stale_after`) are validated when
  present." (The README does not say OpenWiki itself writes `status`
  or `stale_after`.)
- Markdown links express relationships; `index.md` and `log.md` are
  reserved; root index declares `okf_version: "0.2"`; producer
  extension fields preserved across updates.

### Diagrams

Mermaid diagrams embedded where useful; each `mermaid` fence validated
after a run, broken ones degraded to `text` fences and repaired on the
next `--update`.

## Scheduled updates (CI)

"Adding a scheduled CI job that opens a docs PR whenever the wiki
changes", from example files:

- GitHub Actions: `examples/openwiki-update.yml` →
  `.github/workflows/openwiki-update.yml`.
- GitHub Actions with auto-merge: `openwiki-update-auto-merge.yml`
  (needs repo auto-merge, branch protection, an `OPENWIKI_PR_TOKEN`
  fine-grained token; "Auto-merge is repository infrastructure rather
  than an OpenWiki runtime feature").
- GitLab CI: `openwiki-update.gitlab-ci.yml`.
- Bitbucket Pipelines: `openwiki-update.bitbucket-pipelines.yml`.

The README no longer mentions macOS LaunchAgents, per-source
schedules, or `onboarding.json`; standalone CLI is described as
supporting "scheduled runs and personal wikis" without further detail.

## Connectors (ingestion)

"Nine built-in connectors." Personal-mode onboarding offers Custom MCP,
local git repositories, Notion, Gmail, X/Twitter, Web Search, Hacker
News; Slack also available with OAuth app + HTTPS callback.

- `git-repo` — local repo paths, compact manifests
- `custom-mcp` — any HTTP/stdio MCP server, only explicitly safe
  read-only tools
- `x` — X API, OAuth user context (timeline, posts, mentions,
  bookmarks, lists)
- `notion` — hosted Notion MCP server, Notion OAuth
- `google` — Gmail API, OAuth
- `slack` — Slack Web API, OAuth user + bot tokens
- `web-search` — Tavily via LangChain, `TAVILY_API_KEY`
- `hackernews` — public APIs, no credentials
- **LangSmith** (code mode) — enriches a *code* wiki with recent traces
  (tool calls, outcomes, latency); committed `openwiki/.langsmith.json`
  names projects, key from `OPENWIKI_LANGSMITH_API_KEY`.

Ingestion: "deterministic connector tools write raw data and manifests
under `~/.openwiki/connectors/<connector>/raw/`, then source-specific
agent runs synthesize the wiki under `~/.openwiki/wiki/`." Multiple
instances per connector (`web-search-1`, `web-search-2`). Secrets live
in `~/.openwiki/.env`, referenced by env-var name. `openwiki auth
<provider>` runs browser OAuth; `openwiki ngrok start` for Slack's
callback.

## Model providers (standalone CLI only)

"Coding-agent integrations use the host's authenticated model session."
Standalone: "fifteen providers"; onboarding default OpenAI
(`gpt-5.6-terra`). Credentials in `~/.openwiki/.env`; provider chosen
with `OPENWIKI_PROVIDER`, model with `OPENWIKI_MODEL_ID`.

OpenAI (API key); OpenAI (ChatGPT login); Anthropic; IBM Bob; Gemini
(AI Studio); Gemini Enterprise (Vertex AI, ADC); AWS Bedrock (IAM);
GitHub Copilot (gh CLI session / `COPILOT_API_KEY`); OpenRouter;
Nebius / Fireworks / Baseten / NVIDIA NIM / Mistral; OpenAI-compatible
(LiteLLM, Ollama, LM Studio, gateways; Entra ID auth option).

Extras: per-provider base-URL overrides, OpenRouter provider pinning
and token cap, `OPENWIKI_MAX_OUTPUT_TOKENS`, Bedrock stream idle
timeout, `OPENWIKI_REASONING_EFFORT`.
