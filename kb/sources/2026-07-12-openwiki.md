## What it is

OpenWiki is a command-line tool that generates and maintains
agent-optimized wikis for codebases or personal knowledge management.
It synthesizes information from multiple sources into a local wiki
specifically designed for AI agent consumption.

Install: `npm install -g openwiki` (Windows: npm or pnpm; Bun may need
Visual Studio Build Tools for native dependency compilation).

## Two operating modes

- **Personal mode** (`openwiki personal --init`): builds a local
  "personal brain" wiki in `~/.openwiki/wiki`, ingesting from Gmail,
  Notion, web search, Hacker News, X/Twitter, and local repositories.
- **Code mode** (`openwiki code --init`): generates repository
  documentation in an `openwiki/` directory in the current repo, and
  creates/maintains `AGENTS.md` and `CLAUDE.md` at the repo root. If
  those files already exist, OpenWiki only rewrites its own
  `<!-- OPENWIKI:START -->…<!-- OPENWIKI:END -->` block and leaves the
  rest untouched (appending the block the first time). The injected
  block instructs coding agents to reference the wiki when searching
  for context.

## Connectors (ingestion)

- `git-repo` — reads local repository paths, writes compact manifests
- `x` — X API with OAuth (timeline, posts, mentions, bookmarks)
- `notion` — hosted Notion MCP server with OAuth
- `google` — Gmail API with OAuth credentials
- `web-search` — Tavily integration (requires `TAVILY_API_KEY`)
- `hackernews` — public APIs, no credentials

Connectors can be configured multiple times as separate instances
(e.g. `web-search-1`, `web-search-2`). Raw connector data lands in
`~/.openwiki/connectors/<connector>/raw/` before synthesis; per-source
agent runs then synthesize findings into the wiki.

## LLM providers

OpenAI (API key or ChatGPT login), OpenRouter, Fireworks, Baseten,
NVIDIA NIM, Anthropic, OpenAI-compatible endpoints, and custom
endpoints via LiteLLM gateways. Provider selected via
`OPENWIKI_PROVIDER`; retry attempts configurable
(`OPENWIKI_PROVIDER_RETRY_ATTEMPTS`).

## CLI commands

| Command | Purpose |
|---------|---------|
| `openwiki` | interactive CLI |
| `openwiki "prompt"` | interactive with initial request |
| `openwiki -p "prompt"` | one-shot, non-interactive |
| `openwiki personal --init` / `code --init` | initialize a mode |
| `openwiki --update` / `code --update` | refresh the wiki |
| `openwiki code --update --print` | CI-compatible update output (no prior `--init` needed) |
| `openwiki auth <provider>` | OAuth flows (slack, gmail, x, notion) |
| `openwiki ingest all` / `<connector>` / `<connector-id>` | pull from connectors |
| `openwiki ngrok start` | tunnel for Slack OAuth |

In-chat: `/api-key` (update provider key), `/langsmith-key` (LangSmith
tracing credentials).

## Storage and configuration

- Config/secrets: `~/.openwiki/.env`
- Personal wiki: `~/.openwiki/wiki/`
- Raw connector data: `~/.openwiki/connectors/<connector>/raw/`
- Global instructions: `~/.openwiki/INSTRUCTIONS.md`
- Onboarding answers (template choice, per-source ingestion notes,
  schedules): `~/.openwiki/onboarding.json`
- Scheduled-run logs (macOS): `~/.openwiki/logs/`

## Scheduling and CI

- macOS: source schedules install as LaunchAgents under
  `~/Library/LaunchAgents/`.
- GitHub Actions: `openwiki-update.yml` workflow; scheduled runs open
  a PR with documentation updates (including `AGENTS.md`/`CLAUDE.md`
  changes).
- GitLab CI: include `openwiki-update.gitlab-ci.yml`.

Staleness is handled by scheduled regeneration, not by explicit
staleness detection on individual pages.

## Onboarding flow

First run: configure provider + API key, select model, optional
LangSmith key, choose wiki template, configure connector credentials,
set per-source ingestion notes and update schedules; everything saved
to `~/.openwiki/.env` / `onboarding.json`.
