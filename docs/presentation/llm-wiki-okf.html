LLM Wiki

A pattern for building personal knowledge bases with LLMs — written to be pasted into an agent, which then works out the details with you.

Core idea

Don’t retrieve from raw documents at query time. Let the LLM incrementally build and maintain a persistent, interlinked markdown wiki that sits between you and your sources.

Three layers · Three operations

Raw sources · Wiki · Schema  —  Ingest · Query · Lint

gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

The wiki is “a persistent, compounding artifact.”
  • You curate sources and ask questions; the LLM does the writing and the upkeep.
  • Humans abandon wikis because maintenance grows faster than value. LLMs do the bookkeeping at near-zero cost.
  • Loosely echoes Vannevar Bush’s Memex (1945) — an associative, personal store of knowledge.

Why did it resonate so widely? Because every engineering team already lives with the problem it describes. Let’s start there.

Six ways technical documentation lets us down

Scattered

Wikis, SharePoint, PDFs, tickets, code comments, chat threads. No single place to look — so people don’t.

Stale

The code moved on; the doc didn’t. Nothing tells you when it stopped being true.

Untrusted

No signal separating “verified last week” from “written years ago by someone who has left”.

Contradictory

Three pages, three answers. Which one wins? Usually: whoever you asked last.

Tribal

The real knowledge lives in a few heads — and walks out of the door with them.

Write-only

Written for the release milestone, then never read, linked, or updated again.

The LLM Wiki pattern

Stop asking the LLM to re-read everything. Ask it to keep a wiki.

LLM Wiki × OKF
LLM Wiki · the key idea

Compile knowledge once — don’t re-interpret it on every question

Query-time retrieval (RAG) ≈ interpreter

Raw docs are re-read at query time

1Question arrives
2Fetch raw chunks
3LLM synthesises an answer
4Answer is shown… and forgotten

Cost and quality are paid again on every question.

LLM Wiki ≈ compiler

Knowledge is compiled at ingest time

1A source arrives
2LLM integrates it into wiki pages
3Questions read the compiled pages
4Good answers are filed back into the wiki

Knowledge compounds. Synthesis, cross-links and contradictions are already worked out before anyone asks.

03

And RAG? Complement, not replacement

Most teams already have — or are building — retrieval over their docs. Where does the wiki fit?

LLM Wiki × OKF
LLM Wiki and RAG

RAG in one slide

✓ Good at

  • Scaling to millions of documents
  • Near-zero curation, fast to stand up
  • Long-tail lookups: “where was that written?”

✕ Not designed for

  • Keeping what it learned — synthesis is redone every time
  • Telling stale from current — similarity ≠ truth
  • Surfacing contradictions — they are resolved silently in the prompt

LLM Wiki and RAG · conclusion

Not a replacement — they complement each other

LLM Wiki remembers

What the team must know and trust — kept current.

RAG finds

Breadth and recall over everything else.

The LLM Wiki doesn’t replace RAG. RAG finds; the wiki remembers.

OKF — an open format for the wiki

The pattern is abstract on purpose. A team needs something concrete to agree on.

LLM Wiki × OKF
From pattern to practice

The LLM Wiki pattern leaves two gaps for a team

Gap 1

No shared format

Every tool invents its own page layout and metadata. The wiki gets locked to one agent, one plugin, one person’s habits.

→ OKF standardises the files.

Gap 2

No trust model

An LLM-written page looks equally confident on day 1 and day 400. Write-time errors persist; drift goes unnoticed.

→ The lifecycle profile (this project) makes trust explicit.

LLM Wiki × OKF
Open Knowledge Format v0.2

OKF: markdown + YAML frontmatter, one hard rule

  • A bundle is a directory of markdown files with YAML frontmatter.
  • The only hard rule: every page has a non-empty type.
  • Reserved files: index.md (catalog) and log.md (history, newest first).
  • v0.2 standardises provenance (sources), trust (generated, verified) and lifecycle (status, stale_after).
  • Readers must be permissive: unknown keys preserved, broken links tolerated — so profiles can extend it safely.
  • Spec: GoogleCloudPlatform/open-knowledge-format
---type: Entitytitle: Work Orderdescription: A unit of field work …status: stablestale_after: 2027-02-08sources: - resource: /sources/2026-11-08-wo-api-v3.md id: wo-api-v3generated: {by: claude-code, at: 2026-11-08}lifecycle: active # extension key---# Work OrderAssigned by dispatch, synced offline … [wo-api-v3]
LLM Wiki × OKF
Open Knowledge Format

Why a plain, open format matters for engineering teams

Portable

Any agent or tool can read it — Claude Code, Copilot, Codex, a Python script, a human in an editor.

Git-native

Diff, blame, branch, review in pull requests. Git becomes the audit trail of what we know.

Human-readable

It’s just markdown. No database, no vendor, no export step.

Machine-checkable

Frontmatter can be linted in CI, so structure is enforced before merge.

Extensible

Extra keys ride along; plain readers ignore them harmlessly.

Provenance built in

Every claim can point at its source, and say who produced or verified it.

knowledgeAgent · what it adds

Six upgrades on top of the LLM Wiki pattern

1

Lifecycle states

Five states with enforced exit criteria — OKF alone has no trust model.

2

Expiring truth

Active pages carry stale_after; overdue pages feed an automatic review queue.

3

Evidence pinning

A claim resting on a repo file pins its git blob; okf.py drift reopens the page when the file changes.

4

Immutable sources

Captures are append-only. A re-ingest is a new dated file; git history exposes any edit.

5

Graph-aware deprecation

superseded_by plus inbound-link checks — links are never silently broken.

6

Governed vocabulary

Page types and tags registered in SCHEMA.md before use; lint enforces it.

1

Someone changes the file

A commit edits scripts/okf.py — the file this page’s claims rest on.

2

okf.py drift notices

It re-hashes every pinned file: moved: scripts/okf.py. Lint raises a warning — in CI, on the PR.

3

The page is flagged

It goes to needs_review. It is still served, but every answer citing it carries a warning.

4

kb-review re-verifies

Re-reads the evidence, fixes claims, re-pins the blob, appends verified → back to active.
